## Факты, установленные замером

1. `kibborg "hello"` → exit 0; stdout: ответ модели; stderr: `kibborg: host ready (home C:\Users\lex66)`.
2. `kibborg "прочитай README.md и кратко опиши проект в двух предложениях"` → exit 0; stderr показывает `kibborg: tool read`, stdout — описание проекта, построенное по содержимому файла. Это доказывает, что CLI подключён именно к существующему agent-loop с инструментами, а не к «чату с LLM».
3. Профиль без HTTP: ни один порт не поднимается; транспорт — изоморфный in-process fetch.
4. Состав дерева (трассировка при `KIBBORG_TRACE=1`): `loader=yes agents=yes tools=yes llm=yes typertGateway=yes approval=yes commands=yes`, `apiProxy` появился после добавления ряда; `sessionStore=no` — имя сервиса в пробе не совпадает с реальным, это дефект трассировки, а не дерева (сессии работают: `session.create` вернул идентификатор).

## Node-совместимость клиентских плагинов (K0.0.3)

| Модуль | Браузерный бандл `lib/client.js` | tsc-выход `lib/types/client/index.js` |
|---|---|---|
| `@deepseek-ai/dsh-typert-registry` | ошибка при импорте (`window.__ModuleLoader__`) | импорт OK |
| `@deepseek-ai/dsh-api-gateway` | ошибка при импорте | импорт OK |
| `@deepseek-ai/dsh-api-remotes` | ошибка при импорте | импорт OK |
| `@deepseek-ai/dsh-client-runtime` | ошибка при импорте | импорт OK |
| `@deepseek-ai/dsh-client-connection` | ошибка при импорте | импорт OK |

Браузерный бандл — не ESM-библиотека, а регистрация в module-loader страницы, поэтому в Node он непригоден по построению. Tsc-модуль тех же клиентских половин импортируется без обращений к DOM на этапе загрузки.

Известные DOM-обращения в исходниках клиентских половин — только в `client/runtime` и только защищённые: `typeof requestAnimationFrame === 'function'`, `typeof localStorage === 'undefined'` с вызовом строго внутри ветки. Немедленных обращений к `window`/`document` на уровне модуля в tsc-выходе не найдено.

## Влияние на решения

- **R2 подтверждён**: локальный режим работает без сети и без портов.
- **Исход (б) плана реализован и работает.** Для K0.0 его достаточно.
- Для K1.2 (полный клиентский стек) доступны оба пути: tsc-модули клиентских половин в одном процессе (исход «а») либо собственный тонкий слой (исход «б»). Браузерные `lib/client.js` не используются ни в одном из них.
- `createWebConnectionRpc` и `ConnectionController` наружу из клиентской половины connection не экспортируются (в `exports` только `.`, `./invariant`, `./client`, `./src/*`, `./package.json`; из `src/client/index.ts` экспортируются типы плюс `apply`, `inject`, `RpcId`, `AbstractApiClient`, `transportError`). Для `ctx.remote` в K1 нужен либо свой caller, либо один аддитивный субпуть-export с Agent Note по шаблону `PLAN.md` §7.

## Границы выполненного

Не делалось (и не должно было): TUI, `/help`, `doctor`, шимы PATH, интерактивные промпты, полный парсер флагов — это объём K0–K1. Сборка прод-артефактов выполнена только в объёме, необходимом профилю (`tsc -b` + `Kibborg_CLI/tsdown.config.ts`).

## СТОП

Согласно `PLAN.md` §6, фазы K0+ не начинаются до решения по этому отчёту.
