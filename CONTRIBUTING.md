# Contributing to Kibborg CLI

Спасибо за интерес к проекту. Ниже — короткий и обязательный к исполнению порядок работы: он держит сборку, тесты и стиль в одном состоянии у всех.

## Окружение

| Требование | Версия |
|---|---|
| Node.js | `^22.19.0 \|\| >=24.0.0` |
| pnpm | 11.x |
| ОС | Windows 10/11, Linux, macOS |

CLI живёт внутри монорепозитория harness: он использует `@deepseek-ai/dsh-*` через `workspace:^`. Поэтому сборка выполняется из клона [DeepSeek_Kibborg_Harness](https://github.com/Ydjin1984/DeepSeek_Kibborg_Harness), в корне которого лежит каталог `Kibborg_CLI`. Скрипты `scripts/bootstrap.ps1` и `scripts/bootstrap.sh` разворачивают такую раскладку автоматически.

## Первый запуск

```bash
# 1. Раскладка монорепо + зависимости + сборка
pwsh -File scripts/bootstrap.ps1            # Windows
sh scripts/bootstrap.sh                     # Linux / macOS

# 2. Проверка
kibborg doctor
kibborg --help
```

Если вы уже работаете в клоне harness, достаточно:

```bash
pnpm install
pnpm --dir Kibborg_CLI run build
pwsh -File Kibborg_CLI/install.ps1          # или sh Kibborg_CLI/install.sh
```

## Что проверять перед пушем

```bash
cd Kibborg_CLI
pnpm run build      # tsc -b + tsdown, должен быть без ошибок
pnpm run test       # vitest, сейчас 235 тестов
pnpm run lint       # oxlint, 0 warnings / 0 errors
node tests/pty-menu.mjs --boot-ms 55000        # меню и подменю в реальном PTY
node tests/pty-commands.mjs                    # локальные команды и модал панели
node tests/frame-render.mjs --boot-ms 45000 --send "/status"   # кадр терминала в tests/frame.txt
```

`tests/frame-render.mjs` — инструмент визуального контроля: он реплеит вывод PTY в экранную матрицу и пишет `frame.txt` (текст), `frame.html` (для браузера) и `frame.raw.txt` (сырой поток). Пользуйтесь им вместо скриншотов: он воспроизводим и работает в CI.

## Стиль кода

- ESM везде; относительные импорты — с расширением `.ts`.
- `strict: true` и `exactOptionalPropertyTypes: true`; `any` не допускается без объяснения в комментарии.
- JSDoc на каждом модуле и экспорте; для функций — `@param`/`@returns`.
- Комментарий описывает контракт, причину и последствия, а не пересказывает код.
- Один физический абзац комментария — одна строка; файл заканчивается одним переводом строки.
- Один файл — одна ответственность; общие примитивы выносятся в `packages/tui`, работа с харнессом — в `packages/client-node`.

## Тесты

- Юнит-тесты: `packages/*/tests/*.spec.ts`, рядом с пакетом, который проверяют.
- Сценарии терминала: `tests/*.mjs` — реальный PTY через `node-pty`.
- Багфикс без теста не принимается: сначала тест, воспроизводящий дефект, затем исправление.
- Ограничение среды: `conpty` в Windows не пропускает mouse-последовательности, `ESC[?9001h` и альтернативный экран. Такие вещи проверяются юнит-тестами, а не PTY, — не «чините» тест под conpty.

## Коммиты и pull request

- Формат сообщения: `type(scope): краткое описание` (`feat`, `fix`, `docs`, `test`, `refactor`, `chore`).
- В одном PR — одно изменение; независимые правки разбиваются.
- В описании PR: что было, что стало, чем проверено (команды и результат).
- Изменения поведения сопровождаются обновлением `README.md` и соответствующего раздела `TASKS.md`.

## Документация

| Файл | Назначение |
|---|---|
| `README.md` | входная точка: установка, команды, режимы, конфигурация |
| `ARCHITECTURE.md` | слои, поток данных, решения |
| `TASKS.md` | реестр фаз и история исправлений |
| `CHECKLIST.md` | приёмка по фазам и матрица возможностей |
| `TUI.md` | дизайн-спека интерфейса |
| `TROUBLESHOOTING.md` | симптом → причина → действие |

Пишите по-русски, коротко и по факту; команды — в блоках кода.
